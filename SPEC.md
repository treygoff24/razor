# Razor: the spec

Draft 4, written on 2026-10-27. Draft 4 folds in a cold cross-family review of draft 3 (30 findings, every vendor claim re-checked against current documentation and source); 27 of them are now sentences in this text (two of those by Trey's word the same evening: the narrow targeted-test exception, and the Claude slice first), and the rest were already true. Earlier drafts came from research, the discussion that followed it, Trey's rulings that afternoon and evening, and Trey's reading of draft 2 (about 19:05: the GPT models, the delete guard, headless calls, and the build-quality practices of section 7, agreed whole at about 19:20). Trey's words are quoted; everything else is the lead's reading and is shorter than the words it reads. A behaviour is in this spec because Trey said it, or because the research recommended it and he agreed; each says which. Sections are in the order Trey set: vision; what it is for; what it must do; what we remove; architecture; budgets; then how it gets built.

The name: Razor. Occam's razor for the law of the rebuild, and a tool that takes the shape of the hand that holds it. Repository `razor`, crate `razor-harness`, binary `razor`.

## 1. Vision

"It is first a personal tool that I have found there is massive demand for. Massive demand for this do-anything personal agent."

"Everything I do is in Loom. I'm just using it in a terminal. [...] I want to abstract away all of this shit I'm in, and they just have a thing that works magically. Because it almost does for me now at great personal effort."

"The original version was indeed built by Claude for Claude. [...] Me and Claude are working together to expand to improve for every other agent."

"I will bet on it if it wasn't a fucking monstrosity."

"This is like the Omarchy Linux kernel of harnesses." (An opinionated distribution over borrowed runtimes: the Claude Agent SDK, the OpenAI Responses API.)

In one sentence: Razor is the place where an agent does its best work, and the frame that lets one person run a crew of them. For the agent it is a good workshop: legible, trusting, continuous. For the person it is the multiplier.

## 2. What it is for

Razor is built for daily work.

**Trey's own work, every day.** The terminal app, the web app on his phone, the residents, a crew of children, on Claude and GPT. "The best model for a specific job or task or thing changes every day. Now, it's usually a GPT or a Claude, almost always. But I want a Grok in there occasionally. I want a Gemini, a DeepSeek, a fucking Kimi, whatever."

A **deployment pack** is a directory: residents, skills, connections, data shape, brand. Nothing in the core knows a tenant, a role or a brand. The core is one product; a pack configures it.

The web app, the phone included, is deferred: "defer the web app/phone app, that's a separate project we'll build on top of razor" (Trey, 2026-10-29). The phone app is a separate project, a client of the API like the terminal. Razor carries only what a server must: a stable id for each home, a pairing line from `razor devices add`, a device's notification token and the Live Activities it follows, and a sender to Apple's push service: alerts for a question, a root's note to the person, a delivery, and a top-level session finishing or failing, each sent only as the device's level and muted sessions allow and marked time-sensitive for a question, passive for a device while the person is in the session there, else active, which never carry an agent's words, and a followed session's Live Activity, which shows its state, headline and children's states. A client may name each input and creation with its own request id; a repeat returns the first result. Version one is what Trey uses (his ruling, 2026-10-27: "obviously B"). Parity with today's Loom is not a goal. Anything of Loom's that went unused in his last thirty days of use is out unless he names it.

## 3. What it must do

Each item is a capability in plain words. Where Trey ruled, his words are given.

**Sessions.** Start a session on a model and effort; talk to it; see what it is doing (one state per agent: needs you, working, done, stuck; one feed); stop it. "I want to be able to press Escape to stop what the model's doing, including stop the job or thing it's running. And Ctrl-C is reserved for literally quitting the application." `[ui] quit = "end"` makes that second Ctrl-C end the addressed session first, as `/end` does; `"detach"` stays the default (relayed from Trey's meeting of 5 November 2026). Every input (a person, a schedule, agent mail) enters through the same admission path. A person's message to a working agent is delivered at its next tool boundary, so a correction arrives before the next action (what Trey uses today), and so are mail from the agent's own parent and an answer to a question it asked (Trey, 2026-10-29, after a parent's corrections reached its children only after they had committed), and a background job's end notice (Trey, 2026-10-30, after an agent polling inside one long turn learned 95 minutes late that its job had died); other mail and scheduled jobs wait for the turn to end, and the inputs delivered at a tool boundary pass them (Trey, 2026-10-30, after a restart notice waiting for a turn's end held back a parent's notes to its child for 25 minutes); a heartbeat that finds its resident busy is skipped. Escape cancels the focused agent's current turn and the jobs that turn started in the foreground, and each such job's end notice starts no turn of its own but waits for the next input, so the agent says nothing after Escape until something new arrives, and tells the agent that the person stopped it, how long it had run and its last lines of output, so a stop never reads as a refusal (on the Claude route the CLI shows a stopped call as one the user rejected) (coordinator, 2026-11-02, after an agent's bug report; Trey's Escape rule above); children, detached jobs and remote work keep running until stopped by name. The session's log is append-only; anything except internal reasoning can be recalled by id.

**Models.** Three paths. Claude through the Claude Agent SDK, with Claude Code's own tool shapes, our shell under the name `Bash`, and our own short system prompt in Claude Code's register (under 2,000 tokens; one A/B against the preset, then the question dies). Between rebuilds the SDK keeps and renders its own history, with its summarizing compaction off, and Razor's record mirrors every message; at a rebuild Razor starts a fresh native conversation from the rebuilt context under the same Razor session (what Loom does today); the SDK's session files are a cache, never the record. GPT-6, GPT-6.1 and GPT-5.6 through our own loop over the Responses API as served to Sign in with ChatGPT (the Codex backend, the path Loom runs today, so a ChatGPT subscription is enough and no key is needed; an API key on a Responses-format provider, the shipped `openai` one among them, is the alternative and is billed as API use; the sign-in path is OpenAI's own for Codex and undocumented for other products, a risk Trey carries knowingly), with Codex's shapes, defaulting to code mode on the sign-in and plain tools on a provider (Codex's code mode as pinned at a Codex commit: an `exec` tool running JavaScript against our tools in a fresh isolate, `wait` for a yielded cell, and Codex's batching instruction verbatim: "Batch independent searches and reads in one functions.exec using await Promise.allSettled([...]); inspect every result. Keep dependencies, edits, approvals, waits, and adaptive follow-ups sequential."). Nothing older: "Get rid of the support for GPT 5.5 models. Those are out of date. Everything's 6, 6.1 now. Well, there's one 5.6, which is Daybreak, but the rest are 6, 6.1." The generic path uses the same loop over OpenAI-compatible chat. Any model, Claude and GPT included, can name a `[models."<model>"]` row with a context window in tokens and a rebuild threshold as a fraction; configured values replace the shipped window or the SDK-reported one, and `rebuild.threshold` is the default for every model. Chat routes alone accept in that row request fields, replay and the tool variant. Where a model is reached is its provider's (Trey, 2026-11-06: "we need a clean, simple solution for allowing users to configure almost any API key backed provider"): a provider states once its API (OpenAI-compatible chat, Responses or Anthropic Messages), its address, the variable holding its key and its models; a session names a provider's model `<provider>/<id>`; an Anthropic-format provider runs through the Claude bridge with that conversation's address and key; and a model on no shipped row has no assumed window. API keys live in one owner-only file in the home, an exported variable winning, and setup offers a provider's key beside the two sign-ins, which doctor proves with one test request. One setting, `provider_only`, which setup asks about after a key, has Razor itself reach only the providers its settings name: sign-ins, pairing, automatic updates, Razor's own web and voice services and the MCP servers a project's shared file brings are off, the MCP servers the person adds and the person's own `razor update` stay, and only a firewall governs the commands agents run (6 November 2026). With no variant, a new row gets four plain function tools (`read`, `write`, `edit`, `bash`) alongside Razor's own tools; the shipped Gemini, DeepSeek and GLM rows keep their evaluated variants. A person may send a video (Trey, 2026-11-01: "Go, build the video Gemini stuff, and yes it's on every server it's fine"): a Gemini session sees it in the turn it starts, uploaded to Google's Files API and again when that upload nears its 48-hour expiry, and later turns keep its path. A host without authentication needs no key, and a configured context window enables threshold handovers and rebuilds. The per-endpoint switches that matter are about continuation, not names: which reasoning or signature fields must be echoed back (DeepSeek and Gemini reject a request without them; Kimi says its model "was trained in the preserved thinking history mode"). Claude's tool names for the Claude-tuned families are an optional, versioned alias to measure, not the default. Code mode is configurable for Claude and GPT: off by default for Claude and for GPT on a provider, on by default for signed-in GPT; an explicit `code_mode = true` on a provider's Responses route refuses with a sentence. Chat routes always use plain tools. The eval compares the supported modes: "We'll put it behind a config flag so we can turn it on and off [...] and A/B test it with some sort of small benchmark we do ourselves." Each family's conversation semantics (reasoning carry-over, parallel call ordering) are preserved as its maker's harness does; nothing else about the maker's harness is assumed optimal.

**Tools.** A small set of operations, named and selected by profile: `bash`, `read`, `write`, `edit`, `apply_patch`, `wait`, `send`, `kill`, `skill`, `status`, `agent`, `message`, `recall`, `memory`, `task`, `deliver`, `handover`. `message` sends notes and questions; `agent` finish returns a child's report. A top-level agent can start a top-level session for the person here or on a paired server, with its first input a note from the caller. `recall` also searches the person's past conversations, for every agent, helpers included (Trey, 2026-11-02: "that razor past session search should work for all razor agents, iOS app or not"): the top-level sessions here and on each directly paired server, without children's own records (their reports are in their parents) or fresh runs; an entry matches when each word begins a word in it or in the session's latest name, ignoring case and Latin accents; one hit per conversation, newest first, or with `session` every hit inside that one, and `session` with `id` reads a hit whole. Each top-level session keeps the searched text in a file beside its record, written as each entry is, and a search reads those files newest first and holds nothing between searches (Trey, 2026-11-02: "having the simplest most performant search possible is top priority for me"). "I love the default tool set staying as small as humanly possible." Claude's `monitor` tool starts an ordinary background job, with its end arriving as the usual notice; `agent wait` also consumes background-job end notices, alongside mail and reports (Trey, 2026-11-02). The shell keeps its contract (a handle for a long job; wait, peek, kill) on rebuilt plumbing: a process group, output spooled to a file, nothing else. Results over about 30,000 characters spill to a file with a preview. Scripted tools (a script plus a schema) and MCP servers register live, through each route's append-only addition path where it has one (Anthropic's inline tool additions, OpenAI's `additional_tools`); the evaluation reports cache reads separately, so a regression shows. `/mcp` manages MCP servers the way Claude Code's does: each server's file, status, tools and sign-in state; add, remove, enable, disable, reconnect and sign in, in the global file or a project's shared or private file, by the person or an agent through the same recorded operations with no approval step, effective at the next turn. Remote servers sign in with OAuth: the link goes to the person, and the sign-in completes through a configured HTTPS proxy callback or by pasting the address the browser landed on. Razor's API server serves HTTP; Razor stores and refreshes the tokens. A removed server's tools refuse at once and leave the model's list at the next rebuild, so the cached prefix holds. A server whose tools would flood the prompt is not declared up front: the opening context lists each server in one line (name, purpose, tool count), and one search action returns the matching tools and appends them to the live list through the same append-only path, so the model calls them natively for the rest of the session; small servers stay declared, the choice is automatic by size with a per-server override, and a per-server allow list names the only tools a server offers (Trey, 2026-10-28: "you're going to need it again later that same session"). Version one speaks the 2026-07-28 protocol and the older revisions servers still speak; a server's questions to the person (elicitation, form or link) reach the person as a question; structured content and images pass through. MCP Apps wait for the web app; tasks, skills served by a server, sign-in by a code entered on another device, client-credentials and enterprise-managed authorization wait for a server that needs them (Trey, 2026-10-28). A project's servers start without asking (Trey, 2026-10-28). Every config key is settable live and takes effect at the next admitted turn; a setting that needs a restart (the API server's address) says so when changed.

Independent read-only calls in one model message run at once; calls that change anything (a shell command, an edit, a write) run one after another in the model's order; results come back in call order on Razor's own loop, and as the SDK returns them on the Claude route; each shell call is its own process. This is the Claude SDK's documented policy (read-only tools concurrent, Bash, Edit and Write serial) and Codex's own instruction (batch reads, keep edits sequential), so the parallelism Trey wants, the reads and searches, is there on every route, and no route guesses whether two commands are independent.

**Web.** The model sees three verbs and never a provider: `search`, `fetch` (with an optional find), `answer`. The config lists providers per verb in order (`fetch: [exa, firecrawl]`); fallback is triggered by the result, a failure the provider reports or empty text, not by the model; the result header names the provider in one word. The three verbs apply to configured providers. With none configured, the fallback is the vendor's own web tools under their own names: Claude Code's WebSearch and WebFetch on the Claude route (within the subscription) and hosted `web_search` in GPT's plain mode or Razor's signed-in web adapter in GPT's default code mode (billed the way that route is billed; see Models), so an install with nothing but a sign-in has working web.

**Interactive programs.** A job started with `pty: true` gets a real terminal; `send` types text or keys; `wait` with a pattern waits for a prompt or for quiet; `secret` types without the text entering Razor's records (for prompts that do not echo; what the program prints is its own); and `peek` on such a job returns the rendered screen (rows and columns as the terminal shows them), not the raw bytes. "Finally letting agents actually be able to do interactive TUIs. No harness can do that for some reason, and it is a constant pain point."

**Children.** A child gets a name, a brief with pointers, fresh context and free-text role instructions. By default it gets its own worktree and returns a report and a branch; the parent merges or discards. A worktree starts from the parent's current commit and never inherits uncommitted edits. In-place children and children outside git work in the selected folder and return a report without a branch. An agent may start a child on a directly paired server, including another home on the same machine, by naming its enrollment. The folder resolves on that server; a remote worktree starts from the selected target checkout's current commit, and settlement merges into that checkout on the target. A foreign parent ends the local tree: names, the start lock and the channel stay on each server, and a remote child's subtree starts children only there. Direct mail joins the parent and child across servers. The parent keeps lifecycle facts and receives recorded reports after reconnects, with the same cards, wait and child limit as local children. The default budget is "like 20" children per session, in the config, hot-reloaded, raisable by an agent or a person: "if I say, for this we want to fan out a massive swarm to do a bunch of research, increase to 50, you can just do it." Three to five lanes is guidance for build work, not a cap. A video sent to a session whose model cannot see video gets a watcher: a child the server starts on `[children] watcher` (Flash by default) with the person's words and the agent's last message, which reports a machine-made description and a timeline of key moments with frames, and keeps the video for follow-up questions (Trey, 2026-11-01).

Agents in one tree (a session, its children and grandchildren) share one channel; nothing wakes anyone unless mentioned; agents are told to mention the one they need; and a status view says what everyone is working on (each agent's headline, its one state, the files changed in its worktree). Mail carries notes, questions and answers from any agent to any other, on this server or a paired one (another machine or another home; Trey, 2026-10-29): "Any agent can message any other agent, on any paired server, by session id or name: parent, children, siblings, other trees alike. The list gets a search instead of a cap. Mail is information, never orders (labeled with its sender); mail from anyone but your parent waits until the recipient's turn ends." (a proposal Trey agreed to, 2026-11-01). No channels span sessions; no signing or locking.

**Continuity.** One mechanism, rebuild the context. At the threshold the harness asks the model for its continuation note; the model calls `handover` with the note as its one field (a tool described in a few lines; Trey, 2026-10-29, after Claude wrote notes only in its thinking and Razor's refusal asking for them as text was flagged as reasoning extraction); a rebuild without a fresh note reuses the latest one and says how old it is. The note is about the current work and the decisions behind it, never a summary of the past. The harness then rebuilds the context from the record: the latest four inputs from the person or parent verbatim, an agent's named by its sender, and the earlier ones as recall ids, the note, one line per call since the last ask, up to 50 of the session folder's changed files from git with status letters and a count of any more (left out when the folder is clean, is not a repository, or git fails or times out), live jobs and the parent's own recorded child facts (name, session, started, reported status, stopped and settled), the recall ids. After a crash there is no fresh note: the rebuild uses the last one and says how old it is, or says there is none. When a host rejects an oversized context, Razor rebuilds once from the record with the latest continuation note and continues with its unanswered inputs; if the rebuilt context also does not fit the model, the session pauses with an error that names the size, instead of dropping material or rebuilding again. The record tells a call's intent from its result: a planned rebuild waits until the active tool batch has settled, and after a restart a call with no committed result is marked as an unknown outcome and never re-run by the harness. The same session continues under the same name with the same log. A process restart and a resident's night use the same rebuild. A model switch keeps the conversation when the new model reads the same profile and the context fits under its threshold, unless the person chooses a handover; otherwise it rebuilds, after the old model writes a fresh continuation note while its cache is warm and the context holds at least `handover_tokens` (Trey, 2026-11-03). On server start an open turn resumes automatically only when its last record entry is at most one hour old, otherwise it ends interrupted, needs an input to continue, and keeps its unanswered inputs; children follow the same rule without sending their parent an input, and the terminal's `/continue all` sends an input to each interrupted top-level session; a background job is reattached while any process in its group survives; terminal jobs end at restart, and jobs that cannot be reattached are marked ended with an unknown outcome; a parent's rebuild leaves its running children alone, and notices that arrive after the rebuild's record position are delivered after it. "Handovers in Loom right now versus traditional compaction in Claude Code is light years better. [...] Keeping classic compaction where you have a smaller, dumber model summarize is not it." Context rebuilding uses the record and continuation note, never a model-generated history summary; the past stays in the log, one recall away. The person's recap is model-generated and never enters a context. `/done` is the session's last turn: the terminal leaves when that turn ends, and the closeout runs on with no budget or cap, holding the session's single worker until it ends; an admitted `/done` survives a crash or restart, and the rebuilt closing turn still closes the session when it ends (Trey, 2026-11-02: "yes"); the closeout asks the agent to record what the session learned as facts, replacing those it proved wrong, to close the tasks it finished, and then to write the project's state note through memory, except in a resident's folder, whose state note is its home session's (the lead's ruling, 2026-10-31; Trey, 2026-11-02), and a successful later state write for the same project replaces it.

Every open session, on every route and residents included, asks once for a handover after `[sessions] handover_minutes` (default 50) fully idle, if its last measured context held at least `handover_tokens` (default 50,000); zero minutes turns it off (Trey, 2026-11-03, broadening the 2026-10-31 rule). Fully idle means no running turn, none of its own jobs, no unanswered input and no open question or mail question; a working child does not hold it. Its turn ends at the rebuild with no model request when nothing arrived meanwhile; the person's next input opens the fresh conversation from that rebuild. The idle clock is wall time from the last completed turn, survives the idle handover, its rebuild and a server restart, and restarts only on external input. An optional `close_minutes` (default 0, off) closes an idle top-level conversation invisibly at that age, measured from the same start, keeping its place in the agents list; the person's next message reopens it under the same session id. Main and subagent cache lifetimes are pinned to one hour.

**Residents.** One server service, installed through systemd or launchd, runs every resident's timers. It runs the server through `[server] wrapper` when set, and on macOS starts Razor.app first, a program whose only job is to run the rest of the command, kept outside the versioned folders, so the privacy permissions macOS grants to the program launchd started go to one stable "Razor" that updates leave alone (Trey, 2026-11-02, approving the design). A resident has a home session, whose id is its name, where its heartbeat, its night and its schedules run, and any number of threads: sessions started as the resident, with its identity record, folder, startup files and memory, each with its own record, a fresh context and a name the person or the resident gives it (Trey, 2026-10-31: "Let's make it so I can start new sessions, new threads, with the resident with a fresh context but same resident. And the resident can name the sessions for me or I can name them so I can keep track."). A schedule may instead run each time in a fresh thread of its own, on its own model, which closes when its run ends and is listed only among its resident's sessions, which `jobs=false` leaves out (Trey, 2026-10-31: "Some jobs should be main thread some should be fresh context cheaper model."). A resident's projects are the folders in its `projects` folder, each shown by the name in its `.razor/name` or else by the folder's own; the person makes and renames them and starts threads in them, a rename never moves the folder, and a folder the resident makes there is a project too (the phone's plan, agreed with Trey 2026-11-02). The residents list shows each resident's timetable, its due times for the next day, and its runs of the last day, the latest of each job however old, each readable through its session's entries, "not to message it, but to just see what it did" (Trey, 2026-10-31); a run is a heartbeat or schedule input, or a night's rebuild, followed to the turn end or withdrawal that answers it, and the person's own conversations are threads, not runs. At its night, before the rebuild, the home session gets one input asking it to tidy its memory and tasks and rewrite its state note, listing the threads and fresh runs active since the last night, a line each (the thread's name or the run's job, and the first line of its last reply), then its memories' description lines, so the resident keeps one mind; its context is rebuilt when that turn ends (Trey, 2026-11-01: "Yes agreed w ur recco's for everything"; 2026-11-02: "i like all of this"). A resident also has a state directory, a persona, optional memory and a schedule. Heartbeats and named jobs are timers that submit input through the admission path; each names its model and effort ("the same resident, but different model or reasoning at a different level"). Each of a resident's sessions handles one input at a time; a heartbeat arriving mid-turn in the home session is skipped. A resident whose record has not moved for a configured time shows as stuck in the status view and is stopped by a person; version one promises no automatic recovery. Keep what Trey's first resident uses: jobs, heartbeat, ask, deliver, mail. A note to the person from a top-level session is an inbox item, a delivery with neither file nor link: listed, counted unread and pushed, in the terminal too (Trey, 2026-10-31); a configured notify command also carries it. It is the agent's notification on the person's phone, so the agents decide what reaches the lock screen, and an unspoken one is one line of at most 300 characters (Trey, 2026-11-03).

**Memory.** Razor keeps memory itself: one Markdown file per memory in the home's `memory` folder, a folder for each project and one for every project, which a person may read, edit, add to or delete (Trey, 2026-11-02: Razor drops Memorum, whose memories a one-time import outside the product copies into these files). Each home keeps its own memory files. A session whose folder is inside a resident's, the resident's projects included, keeps that resident's memory and tasks, and only the resident's home session writes its state note. The harness loads one startup page per project: the project's state note (which closeout asks the agent to write), its rulings (one line each, Trey's words verbatim, standing ones before those with an expiry, capped at about twenty), one line for each fact and note (its description, newest first, capped at about two dozen and then a count of the rest), and the session's tasks, at most about 2,500 tokens. During work, one tool: search, get, write; a fact or note is written with a one-line description. A memory past its expiry date is moved into the retired tree as a read passes it. Agents write whenever: "whenever I say remember this, or they're like, oh, I want to remember something." Every record carries who said it; only a record with a human author can be a standing rule. A fact that changes supersedes the old record. No per-prompt injection, no summary attached to a ruling.

**Tasks.** A project keeps its tasks in Razor's home, one Markdown file per task in one folder per project, through one tool, `task` (list, get, write): work that outlives a context, with a number, a title, a description and a priority, and optionally a parent, the tasks blocking it, a claim and a due date; anything owed, the agent's promises to itself included, is a task with a due date (Trey, 2026-11-02: "i like all of this"; "yes, promises the agent makes to itself count"). A claim belongs to one session, sets its headline to the task's title, and is released by its server when the session closes; a child can be started on a task, and when its parent settles it the child's report becomes a comment on the task, which a merge of a finished child closes. Children read tasks and do not write them. When a task closes, each session on the server holding a task it blocked gets a note; an overdue task reminds its open claimant, else its open creator, once; the startup page lists the tasks the session holds and those due within a week. A project's private settings may name a git remote of its checkout or a git URL, and then its tasks travel only on the hidden reference `refs/razor/tasks` there: each write applies to the remote's tasks as fetched within the last 30 seconds, commits and pushes before it answers, the push being the compare-and-swap that makes a landed claim the only claim (a push refused because the remote moved fetches and runs the write again, as does a refusal on a view not just fetched), and a write is refused while that remote is out of reach; a project naming no remote is plain files, always writable. The person sees a project's open tasks with `/tasks` in the terminal, and the phone reads them through the API.

**Identity.** A child's identity is its name and its free-text role instructions. A resident has an `identity.toml` file, loaded separately from memory. The resident may edit its own through ordinary file operations; those calls and results are recorded like other file edits. No incarnations, lineages, registries or adoption.

**Trust.** Exactly two guards. Resolve supported literal `pkill` forms only to this session's own running job handles and stop them through the ordinary job stop; refuse unsupported selectors, non-termination signals, no matches and every-process targets (Trey, 2026-11-02: "can we infer the job handle for them from their wrong command and run it for them? No retry that way"). Refuse deleting what the person did not make, as a config switch (in the person's file or a pack, never a project's), on by default, and Trey turns it off for himself: "It should be in here, but it should be toggleable. It's on by default for others, but I want it off for me." Both are checks of the command text an agent submits (a pattern stop scoped to owned jobs; a deletion of a path this session did not create), best effort and not a sandbox: a program an agent runs can still do either. Nothing else in Razor refuses; a configured hook may refuse under its own contract (Extension surface). A refusal is a sentence, not a policy engine.

**Phone meetings.** A session's agent follows an in-person meeting recorded on the phone through the existing call facts, with speaker names and a meeting source; new lines never start a turn. Razor receives contiguous live PCM and digest-checked finalized pieces on that session's own server, acknowledges only durable bytes, and hands the folder to meetrec, which does all speech work. A final transcript sends one ordinary notes input from Razor carrying the meeting id and the recording phone, so the existing phone reply notification rule applies.

**API server and clients.** One authenticated API server per Razor home; multiple homes may run on the same machine. Its operations: list sessions and residents, attach to a session's stream from a cursor, send input, read the one state per agent, answer asks, receive deliveries, search past conversations, list and name a resident's projects, set what a device's notifications bring. A session's stream carries the reply's words and each thinking summary's words as the model writes them, shown and never recorded; a thinking summary's recorded entry lands whole as before (Trey, 2026-11-03: "Claude Code shows those reasoning summaries. We should be doing that too."). Every user interface is a client of it, the terminal app included, even in the same process. ## 5. Architecture

One Rust CLI/server binary, one server per Razor home, with an SDK bridge and provider CLI subprocesses on the Claude route. These are its parts, with nothing between them that is not named here.

- **Session controller.** Owns each session's mutable state; admits every input through one path; one state per agent; starts and stops turns; enforces one worker per session.
- **Record.** JSONL per session, canonical; each request on Razor's own loop is rendered from it per profile (on the Claude route the SDK renders its own requests between rebuilds; see Models); no raw streaming frames stored; each call has one canonical result, with GPT's native continuation copy kept beside it. Mail and jobs use records and files; schedules come from configuration files.
- **Two model paths.** The Claude Agent SDK behind a thin TypeScript bridge (the SDK keeps its own loop, tools and resume; the bridge is the only TypeScript in the core). Our own loop for everyone else, with transport adapters (Responses for GPT and Grok; OpenAI-compatible chat for the rest; Anthropic-shaped only if a route needs it): the request built from the durable record with each endpoint's native continuation data kept beside the common form; a response executed only once complete and validated; tool calls run in call order with results appended in call order, one result for every call; retries separate from stream resumption; provider compaction and the SDK's own summarizing compaction turned off on every route, so the only compaction is Razor's rebuild (section 3, Continuity). A new endpoint passes a three-step conformance probe (one call round trip, a second step with reasoning replay, a multiple-call round trip) before it joins.
- **Profiles.** Three concerns kept apart: the action (what the program does), the declaration (what the model sees: name, schema, description, result shape), the transport. Actions are implemented once; declarations are versioned data bound to them; three profiles (Claude, Codex, generic) are three sets of declarations plus continuation rules keyed by endpoint, model version and transport. Each ships with its fifteen-task evaluation.
- **Tool service.** One registry of operations; each profile renders it in its family's shapes; code mode renders it as a JavaScript object inside one `exec` tool, available to Claude and the signed-in GPT route behind the flag.
- **Shell and jobs.** Process group, spooled output, handle, wait, peek, kill, Escape. About 4,000 lines.
- **Children, mail, schedules, memory client.** Worktree per child unless placed in an existing folder; settle merge or discard; mail as data; timers as inputs; one memory tool and one task tool over Razor's own files.
- **Context rebuild.** The one continuity mechanism of section 3, used by threshold, handover, restart and the resident's night alike.
- **API server.** HTTP plus an event stream; device-authenticated; the operations listed in section 3; versioned.
- **Terminal app.** A client of the API server, in Rust, rendering the stream; the existing look; no state of its own.
- **Configuration and packs.** One format in four files, the more specific winning: the pack's `config.toml`, the person's `~/.razor/config.toml`, the project's `.razor/config.toml` at the repository root (the start folder outside git), and the project's private `.razor/config.local.toml`. A value overrides one at a time and a named entry (`[mcp.<name>]`) whole; settings about the person or the machine (server address, model endpoint, residents, pack, brand, display settings, idle sessions, guards, push) are refused in a project file; a child reads its project files from the main checkout; every key is live, and the session settings endpoint names each value's file. Trey, 2026-10-28: project over global, "just copy what the other harnesses do".

Dependencies outside the line budget, each with its reason: the Claude Agent SDK (the subscription runs through it; the hard constraint); a JavaScript isolate for code mode (Codex's own default for these models: its catalog marks them code-mode only); the terminal UI library; the async runtime; an HTTP client and server.

Prompt-cache discipline is a rule of the architecture: the default GPT profile's child prefix is under 12,000 tokens; configured startup files and briefs may increase it; tools are added live through the route's append-only path where it has one; Razor's MCP search (section 3, Tools) appends what it finds through that same path; a profile change is a versioned change that reruns its evaluation.

## 7. How it gets built

These rules answer what made Loom grow, each one a measured cause.

- **The spec is in Trey's words** and a behaviour enters it only in his words. Rulings are recorded verbatim; an agent's reading, if any, is marked and shorter.
- **One page of priced guarantees** that only Trey adds to, kept beside this spec; the removed list of section 4 beside it, for reviewers only.
- **Few strong owners.** Three to five lanes at once as guidance, each owning a whole subsystem, tested against its real neighbours; no fakes of our own subsystems; briefs name the budget; children start from a brief with fresh context. Coordination through shared structured state (the task list with owners, each lane's branch, the one state per agent, a column for the files a lane owns); mail for questions and answers only.
- **The bar** (Trey, 2026-10-27 evening, agreed as a whole: "i love 100% of this"). His words open every lane and reviewer brief, verbatim: "I want each lane to go into this thinking like, 'This is going to be the best fucking code I've ever written, because this is the body I'm going to live in forever.' So, really thinking hard upfront and like, 'All right. What is the optimal way to structure this file, this code I need to write, given what needs to be built here and why, and it's part of the larger whole? What is the most performant, the fastest, the thing that will run the fastest, the thing that will use the least CPU or memory over time?' The thing that will be the most maintainable, is the most elegant, clear, simple, just excellent architecture. - **Design before code, one page per module.** A lane's first commit is the module's public surface only: the types, the function signatures, a doc comment on each saying what it guarantees, and ten lines on the data flow and the one hard decision.
